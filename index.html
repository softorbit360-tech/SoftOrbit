Distance-based failover

Lower route distance is preferred. If the active route becomes unavailable according to its check, the next eligible route can take over.

/ip route
add dst-address=0.0.0.0/0 gateway=ISP-1_Primary_GATEWAY distance=1 check-gateway=ping comment="ISP-1 Primary"

add dst-address=0.0.0.0/0 gateway=AGNI_PRIMARY_GATEWAY distance=2 check-gateway=ping comment="ISP-2 Pimary"

add dst-address=0.0.0.0/0 gateway=AGNI_SECONDARY_GATEWAY distance=3 check-gateway=ping comment="ISP-2 Secondary"

add dst-address=0.0.0.0/0 gateway=LINK4_GATEWAY distance=4 check-gateway=ping comment="ISP-1 Radio"

Gateway alive ≠ Internet healthy

Router→Gateway ✓→ISP Core ✕→Internet ✕

check-gateway=ping can confirm gateway reachability, but a gateway may still respond while an upstream path is unavailable.

⚠️ For production, choose monitoring targets and failure logic carefully. A public monitoring host can itself be unavailable.

Recursive route concept

MikroTik↓Gateway↓ISP↓8.8.8.8 / 1.1.1.1

Recursive routing can test reachability beyond the directly connected gateway. Scope/target-scope and route design must match the actual RouterOS configuration.

What is Firewall Management?

CrowdStrike Firewall Management provides centralized management of endpoint firewall policies and rules. Instead of manually configuring every endpoint, administrators can organize hosts into appropriate groups and apply controlled firewall policies.

💡 Think of the architecture as:

Falcon Console → Policy → Host Group → Endpoint Firewall → Traffic Decision

Firewall Decision Flow

Endpoint ↓ Network Traffic ↓ Firewall Policy ↓ Rule Matching ↓ Allow / Block

When troubleshooting a blocked connection, verify the endpoint, assigned policy, applicable rule, traffic direction, protocol, port and network context.

Typical Administration Workflow

Firewall Policy Structure

Firewall Policy
│
├── Host / Host Group
│
├── Platform
│
├── Rule Groups
│   │
│   ├── Rule 01
│   ├── Rule 02
│   ├── Rule 03
│   └── Rule 04
│
└── Enforcement / Action

A clean policy structure makes troubleshooting much easier. Avoid creating unnecessary duplicate rules when an existing rule group can be reused.

Policy Design Principles

1. Define the required traffic first.
2. Keep rules specific.
3. Avoid unnecessarily broad rules.
4. Separate server, workstation and special-purpose policies where appropriate.
5. Test policy changes with a controlled host before wider deployment.

Policy Troubleshooting

If a firewall rule appears correct but traffic is still blocked, don't immediately create another allow rule. First determine which policy and rule are actually affecting the endpoint.

⚠️ More rules do not necessarily mean better security. Incorrect rule ordering, scope or assignment can make troubleshooting significantly harder.
RULE BUILDER CONCEPT

Firewall Rule Anatomy

Understand the major elements used when designing an endpoint firewall rule.

Traffic Direction

Inbound Outbound

Always establish whether the connection originates from the endpoint or is coming toward the endpoint.

Protocol

TCP UDP ICMP

The protocol must match the actual application traffic. A TCP rule does not automatically permit equivalent UDP traffic.

Port

TCP/443
TCP/80
TCP/3389
UDP/53

Define ports according to the actual application requirement instead of allowing unnecessary port ranges.

Traffic Scope

Source Destination Network Application

The narrower and more accurate the rule scope, the easier it becomes to understand its security impact.

Action

Traffic Match → Rule → Allow / Block

The action determines what should happen when the defined traffic matches the rule.

Example Rule Logic

Direction: Outbound
Protocol: TCP
Destination Port: 443
Purpose: HTTPS
Action: Allow

This is a conceptual example for understanding rule structure. Actual production rules should be based on your environment and approved security requirements.

🔴 Application Cannot Connect

Symptoms:

  • Application opens but cannot connect.
  • Server connection fails.
  • Browser/application shows timeout.

Check:

  1. Endpoint firewall policy.
  2. Applicable host group.
  3. Direction of traffic.
  4. Protocol.
  5. Destination IP.
  6. Destination port.
  7. Existing allow/block rule.
💡 Do not start by creating a broad Allow Any / Any rule. Identify the actual required traffic first.

🔴 RDP Not Working

When troubleshooting Remote Desktop connectivity, verify that the expected RDP traffic is permitted, the destination host is reachable and the endpoint firewall policy is actually assigned to that host. 

Test-NetConnection SERVER_IP -Port 3389

Get-NetTCPConnection -LocalPort 3389
⚠️ Replace SERVER_IP with the actual authorized destination host.

🔴 DNS Works / Application Fails

DNS resolution alone does not prove that the application traffic is permitted.

DNS Resolution ✓ ↓ IP Reachability ↓ Port Connectivity ↓ Application Session

Test each layer separately instead of assuming that successful DNS means the firewall is correctly configured.
